# v0.3.0 batch 2: S and M issues of the native harness core, one release each

Why: the quick wins batch (odd/tasks/v0.3.0-quick-wins.md) closed the cheapest issues of
"v0.3.0 · Native harness core". This batch takes the next seven, sized S or M: #45 (remainder),
#63, #72, #73, #3, #4, #25. Planned by a read-only pass over the issues and the code on
2026-11-23, at main e982717 with v0.2.3 as the last stable tag. The executor is a fresh
session: everything it needs is in this file. The owner's decisions are recorded at the end
(section "Owner decisions, 2026-11-23"); they are answers, not open questions.

Release rule (owner, 2026-11-23): a `fix` or `perf` merged alone ships as an automatic patch
(`aval release patch --yes`, published from `release-patch` with no approval). Each `feat`
issue ships as the next prerelease of v0.3.0 (`aval release rc --yes`), which waits for the
owner's approval of the `release` environment. Tag it and continue: no step in this batch
depends on that approval. v0.3.0 stable is not promoted here. `docs`, `chore`, `test` and `ci`
alone produce no release and ride along with the next one. Three limits come from the code
(internal/release/next.go, git.go), not from the docs:

- `aval release patch` does not look at commit types. It tags HEAD of main as last stable + 1
  even with only chores, and even with unreleased feats on main. Run it only when a
  `fix`/`perf` was just merged AND no `feat` has been merged since the last stable tag.
- Once the first feat is on main (T3), the patch lane is closed for the rest of the batch: a
  later fix ships in the next rc (D16). This is why T1 goes first.
- After the first rc, `aval release rc` always cuts the next rc, even when only chores were
  merged since. After T6 (chore) run no release command.

Order and why: T1 #45 first, because it is the only task that can yield a patch. T2 #63 next:
it writes no repo code, and its kit lets the owner run the manual sessions while the rest
proceeds. Then the two S feats, #72 and #73. Then #3, which unblocks #4, and #4 right after.
#25 goes last: it rests on the hook exec amendment (D7), and being last lets #4 ship inside
its rc.

## Flow for every task (referenced below as "the flow")

1. `git checkout main && git pull --ff-only`, then `git checkout -b <branch>`.
2. Load the project skills the task names (AGENTS.md table). `strict-tdd` and `aval-testing`
   always apply: RED fails on an assertion, never on a compile error, a missing file or setup.
   When the code under test does not exist yet, first add a stub that compiles and returns the
   wrong answer.
3. Visible surface (CLI output, TUI, copy): `design-pipeline` skill, then
   `aval design ack <surface>` before the edit, `aval design gate` after.
4. `go vet ./...`, `gofmt -l .` (prints nothing outside `.claude/worktrees`), `go test -race ./...`,
   `go test ./tests/ -run 'Quality|Architecture'`.
5. Commit per work unit, Conventional Commits, no `Co-Authored-By`, no AI attribution.
6. Release notes, for a task that releases, in the same PR (`aval-release-notes` skill):
   `docs/releases/vX.Y.Z.md` and `.es.md` for the base version, plus a new CHANGELOG section
   on top, `## vX.Y.Z (YYYY-MM-DD)` or `## v0.3.0-rc.N (YYYY-MM-DD)`. The section must contain
   the literal link targets `(docs/releases/vX.Y.Z.md)` and `(docs/releases/vX.Y.Z.es.md)`;
   an rc links the base files `v0.3.0.md` and `v0.3.0.es.md` (tests/release_notes_test.go).
   One section per rc (D2); earlier sections are not edited; the two v0.3.0 files are updated
   in place per rc.
7. `git push -u origin <branch>`, `gh pr create`, wait for the three `test (...)` jobs.
8. `gh pr merge <N> --merge --subject "merge: <summary> (#<N>)" --body ""`.
9. `git checkout main && git pull --ff-only`; wait until `ci.yml` is green on that commit
   (`gh run list --commit <sha> --workflow ci.yml`, then `gh run watch <id> --exit-status`).
10. Release step of the task: build the binary from main (`go build -o <scratch>/aval ./cmd/aval`),
    run `--dry-run` and check the version printed equals the one in this plan, then the real
    command. Report the workflow URL and the `preflight` job result. Do not wait for the
    environment approval.
11. Tick the boxes here (ticking keeps the deck valid; a new or renamed heading needs a new
    deck).
